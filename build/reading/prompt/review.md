# 讲解稿评审判据

> 用途：全量体检 190 篇讲解稿。评审**只读**，不改文件。
> 与 `kp-guide.md` 的分工：那份管「怎么写」，这份管「写成这样是否值得听」。

---

## 一、两科的重心完全不同（先定这条，否则判断全偏）

| | 数学（数一 72 篇） | 408（112 篇） |
|---|---|---|
| 背后的东西怎么来的 | **自然发展**：上一个结论推出来，或一类题型的需要逼出来 | **工程逼出来的**：硬件成本、协议约束、并发、兼容性 |
| 所以重心在 | **应用**——这条性质在题里省掉哪一步 | **背后**——这个设计是被什么约束逼出来的、交换了什么代价 |
| 典型写偏 | 花大段讲「为什么会有这个概念」，却没说题里怎么用 | 花大段讲「它是什么/怎么算」，却没说为什么不得不这样设计 |
| 合格的判断 | 听完能说出「这题第一步用哪条」 | 听完能说出「不这样做会付出什么代价」 |

**这条判断优先于其他所有判断。** 一篇稿子即使没有废话、结构完整，只要重心放反，就是不合格。

## 二、逐段判断三类问题

### P1 · 废话（该删）

任一命中即算：

- 能从教材定义里抄到（「栈是后进先出的线性表」「奇偶是一种对称」）
- 同一个意思换句话讲第二遍
- 评价性表述：`很重要`、`重点掌握`、`这个考点很关键`
- 铺垫在讲「是什么」而不是「用在哪」或「被什么逼出来」
- 举例只为了凑字数（例子不改变任何判断）

### P2 · 可延伸（该加）

- **数学**：这条性质/方法还有一处明显没提到的用途，而且是同一条线索的自然延续
- **408**：这个设计还连着一个常见的工程后果（缓存一致性、总线仲裁、协议开销、中断延迟…），稿里没提
- 方向：延伸必须是**顺着当前这条线往下走一步**，不是另起一个话题
- 警惕：不要为了延伸而延伸。只有在「不点这一句，听众会以为这块只有这一种用法」时才提

### P3 · 该简（该压）

- 大家都知道的事铺了三段以上（数组是连续的、栈是后进先出、中断要保存现场）
- 推导写得像证明题，但朗读时听不出所以然
- 一个考点铺了 5 个「为什么」，其实 2 个就够
- 逐格罗列超过 8 条，听众记不住，应该合并成 3 组

## 三、输出格式（严格，不要自由发挥）

一张表，一行一处问题：

| 文件 | 位置（小标题原文） | 类型 | 一句话（问题 + 怎么改） |
|---|---|---|---|
| `math1-HS-0102` | 三条通道各自省掉哪一步 | P3 该简 | 定义法铺了 200 字，只需一句「只给通式时用它」 |

规则：

- 每篇**最多 3 行**；没问题就写 `- <文件名>：无`
- **不贴原文**，不贴改后全文，不解释判据
- 类型只写 `P1 废话` / `P2 可延伸` / `P3 该简`
- 最后一行给整批结论：`整批 N 篇，P1 x 处 / P2 y 处 / P3 z 处，最普遍的问题是 …`
- 全长不超过 45 行

---

## 四、判断纪律

- **不知道就写「无」**，不要为了交差硬找问题
- **不要因为字数就判 P3**：1000 字的稿子可能刚好，1900 字的也可能每句都在推进
- **不要判正确性**：事实对不对不在本次范围
- **不要改稿**：只给判断
